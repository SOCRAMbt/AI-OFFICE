    assignReviewers

    • assignReviewers(state: OfficeState): Promise<string[]>

      Asigna reviewer a las cards que tienen owner pero reviewer=null.

      Por qué existe

      El routing de savePlan corre cuando el roster está VACÍO (los agentes todavía no existen): deja reviewer=null en todas las cards. El dispatch después materializa los agentes pero no vuelve a rutear, así que el review quedaba estructuralmente imposible: submitReview exigía card.reviewer === reviewerId y ese campo era null para siempre.

      Este método es la segunda mitad del routing: corre DESPUÉS del dispatch, con el roster completo, y cierra el hueco.

      Parameters

      • state: OfficeState

      Returns Promise<string[]>

    halt

    • halt(state: OfficeState, reason: string, by?: string): Promise<OfficeState>

      Detiene la corrida.

      El freno tiene que existir por una razon concreta: una malla de agentes que se auto-continua puede quedarse quemando tokens y tokens hasta que se agota el presupuesto, sin que nadie lo note. Un freno explicito convierte eso en una decision de una persona.

      Con el freno puesto: el hook de auto-continuacion no reanuda, el dispatcher no despacha, y la compilacion automatica del motor se desactiva.

      • state: OfficeState
      • reason: string

    runGates

    • runGates(state: OfficeState, cardId: string): Promise<GateResult>

      Corre los gates de una card.

      Tres dimensiones, no una

      • Tecnicas (build, typecheck, lint, test, diff): el codigo esta sano.
      • Seguridad (secretos): no hay credenciales en el arbol.
      • Requisitos (verify): el objetivo del usuario esta cumplido, con evidencia enlazada a cada criterio de aceptacion.

      La tercera es la que falta en casi todos los sistemas de CI: un proyecto puede pasar las dos primeras y tener la autenticacion mal porque ningun test contemplaba ese escenario.

      Parameters

      • state: OfficeState
      • cardId: string
